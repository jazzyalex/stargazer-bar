# Stargazer snapshots and author summaries

Proposed design · 2026-11-23

## User experience

Add **Stargazers…** to each tracked repository’s existing menu-bar submenu. Open a resizable SwiftUI window for that repository with two views.

- **Current** shows the number of accounts and the timestamp of the last complete check. The searchable list scrolls through every account in the snapshot. Each row shows the GitHub handle. Rows load their display names and short bios as they come into view. Leave missing or unloaded fields blank. The numeric column shows stars received once measured. Selecting an account opens its profile card with follower count, a GitHub link, and any public links the author has provided, such as X, LinkedIn, or a personal website. **Load visible star totals** lets the user compare the visible accounts’ star totals. Opening the window displays the stored list when the current connection has been verified.
- **Disappeared** shows the retained events newest first. Each row shows the last-known `@login`, the repository’s `owner/name` when detected, and two local date and time values labeled **Last seen** and **First missing check**. The help text reads “This account was present in an earlier complete check and absent in a later one. Unstarring, account deletion, suspension, or visibility changes can produce this result.”

Before the first accepted snapshot, show **Waiting for first complete check**. After it, show **No disappearances detected yet** if the history is empty. A skipped or failed check shows the reason and the last valid check time. A repository whose GitHub connection lacks list access gets an explanation and a route to the existing GitHub settings. Use the existing **Check Now** action in the window, scoped to that repository. The feature lives in the repository submenu and window, with silent updates.

## Current app and GitHub constraints

- Launch starts `RepoPollingService`, which runs a one-shot timer after polling. **Check Now** uses the same refresh pipeline. The existing **Settings → General → Refresh** intervals are 10 minutes by default, 60 minutes, and one day. A selected interval measures time from completion of a refresh. Sleep, app exit, backoff, and slow or rejected checks can extend the time between observations. Settings adds repositories through a separate validation and background details path. An added repository gets its first identity baseline on the next normal refresh or **Check Now**. [Polling service](../../../GHMenuStars/Services/RepoPollingService.swift#L59) · [Refresh settings](../../../GHMenuStars/SettingsView.swift#L389) · [Add flow](../../../GHMenuStars/SettingsView.swift#L767)
- `GitHubRepoAccess` selects the existing OAuth or fine-grained PAT credential. Background reads use the silent Keychain path. Normal public tracking can run anonymously. GitHub restricts access to stargazer identities to repository admins and collaborators, and restricted responses can be empty or forbidden. Apply identity checks to both public and private tracked repositories whenever the existing credential is authorized. Private reads use the actual `stargazers_count` from GitHub, independently of the private repository headline metrics. [Repository authentication](../../../GHMenuStars/GitHub/GitHubRepoAccess.swift#L101) · [App wiring](../../../GHMenuStars/AppDelegate.swift#L9) · [GitHub access announcement](https://github.blog/changelog/2026-06-30-upcoming-access-restrictions-to-public-api-endpoints-and-ui-views/) · [GitHub confirmation](https://github.blog/changelog/2026-09-04-new-api-endpoint-provides-privacy-safe-star-history-data/) · [GitHub stars documentation](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars)
- The current star trend uses `fetchStargazerDates`, which may sample recent pages or stop at a date cut-off. A numeric star count or repository metadata `304` supplies no evidence about individual membership. Equal counts can hide a removal and an addition. ## Collect and validate a snapshot

1. Extend the existing GitHub client to expose the numeric repository ID, canonical name, visibility, raw count, and applicable permission fields from repository metadata. Resolve the authenticated viewer’s numeric ID through the existing `GET /user` path with the token selected by `GitHubRepoAccess`. Cache that identity for the credential in memory. Pin one credential for the request group and discard an in-flight result when the connection changes. An anonymous check yields **Connect GitHub to see stargazers** and makes zero identity requests. Use the existing OAuth and PAT scopes.
2. Start with fresh repository metadata from the normal refresh. When that request returns `304`, obtain the body from the same credential with an unconditional fetch for an eligible identity check. Capture the GitHub repository ID, visibility, and raw count. If the first response is an error or required identity fields are absent, skip the check. Request `/repos/{owner}/{repo}/stargazers?per_page=100` through `GitHubClient`, using the existing star media type and a strict decoder for `user.id` and `user.login`. Keep the page read time for each account. `starred_at` can feed the chart during the refresh.
3. Follow `Link`’s `rel="next"` sequentially. Accept consecutive pages only, on the expected HTTPS API origin and stargazer resource for the canonical name or verified numeric repository ID. Keep the same page size. Distinguish a missing next link from a malformed, conflicting, or unsafe one. Reject unexpected redirects, repeated pages or IDs, invalid IDs or logins, short nonterminal pages, and further pages after the expected terminal page. A nonempty terminal page can establish a display-only count mismatch. Require a fresh HTTP `200` and a fully decoded body for every page. Bypass the local URL cache for validation reads. A `304` or `206` fails the attempt. [GitHub REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api?apiVersion=2022-11-28)
4. A single-page response whose count matches metadata needs one membership read. For a multi-page response or a count mismatch, make a second independent full walk with the same bounds and credential. Require identical account IDs and corresponding logins across the two passes, and use the second pass for account observation times. Fetch fresh repository metadata after enumeration and require the same numeric repository ID, visibility, and count as at the start. A disagreement between passes or metadata readings rejects the attempt. If only the terminal count differs from stable metadata, show the returned accounts and both counts in **Current**. Keep the list in memory and leave the saved baseline and history untouched. The API provides a live paginated list, so these checks catch observable drift while leaving a residual chance of undetectable concurrent changes. [GitHub engineering on the live stargazer list](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)
5. Treat an empty list as valid only if both metadata readings say zero and this credential’s repository access is positively corroborated during this refresh. Use authenticated owner ID or explicit `admin`, `maintain`, `push`, or `triage` permission when available. For ambiguous permissions, reuse the existing authenticated repository-directory request with the same credential and accept a positive numeric repository ID match under explicit access, including organization membership where applicable. Run this lookup only for an ambiguous zero and share it across repositories for that credential during the refresh. If the lookup fails or yields no evidence, show **Stargazer access could not be verified** and retain the previous data. Public `pull` permission alone also appears on repositories accessible by default. [GitHub repository access and permissions](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user)

Track identity-check status separately from existing metric-check status. Keep the last accepted baseline and event history on any transport, API, decoding, pagination, consistency, or storage failure. Handle access denial independently from GitHub rate limiting. Verified credential or repository access loss marks a break in continuity and hides the cached identities until a new authorized check succeeds. An ordinary offline, quota, or consistency failure leaves comparison continuity intact.

### Agent Sessions cross-check

The public Agent Sessions repository (GitHub ID `1060421643`) requires additional verification for every saved snapshot. Use the same credential for a complete GraphQL cursor walk and require the same viewer, repository, visibility, and reported counts. The full set of numeric IDs must match REST. Read star history from the current week through the repository’s creation week and require its weekly and daily totals to agree with the ID count. Recheck repository metadata before saving. The first passing check establishes a baseline with zero detections, even if the headline count differs. A failed cross-check preserves the saved history and may still show the returned REST list for browsing.

## Polling and request budget

- Add the identity check to the existing single-flight refresh. Use the metadata and releases results already obtained by the poll, then perform the identity reads serially. Apply available core metrics even when the extra reads fail. When the same public-repo poll needs star trend dates, reuse dates from the accepted stargazer walk and keep fork fetching independent. If identity verification cannot supply dates, use the existing chart fetch when API quota permits. The identity path never consumes a sampled trend as evidence.
- Estimate the list cost from `max(1, ceil(stargazers_count / 100))`. A single-page check uses one list request and a trailing metadata request, with a second list request if the count disagrees. A multi-page check uses two full walks and a trailing metadata request. Separately account for an initial `304` that needs a metadata body, first use of a credential that needs `GET /user`, and ambiguous zero access checks. When available quota cannot cover completion, defer before the first list page and keep the old baseline. Use current REST headers during the walk to stop before additional calls would exhaust the budget. A page or budget limit always yields an incomplete attempt. There is no separate identity timer or identity check on window open.
- Extend existing GitHub rate-limit handling for primary exhaustion and secondary `403` or `429` responses. Honor `Retry-After` and reset headers and use at least a minute of cooldown for a secondary limit without a usable delay. Share the cooldown with manual and automatic polling and author detail requests. Apply rate state after any normal store write that would clear it. Stop issuing requests for the affected credential as soon as throttled. Defer retries to the existing refresh flow and lengthen the delay if secondary throttling repeats. Suppress repeated access-denied identity probes for 30 minutes on automatic refresh, with immediate re-evaluation after a credential change or a user-initiated check outside a rate-limit window. [GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## Compare and persist

- Keep one accepted snapshot and up to 90 days of disappearance events, capped at the newest 2,000 events per tracked repository. Use a versioned record in the app’s local Application Support directory, keyed by the tracked repository UUID. The snapshot includes the GitHub repository ID, viewer account ID and credential source, visibility, check start and completion times, and each account’s numeric ID, login, and page observation time. Events store the account ID, last-known login, repository label, observation interval, and the same repository and viewer scope. Capture a completed observation independently of the normal metric timestamp.
- The first accepted snapshot is a baseline. For each later accepted snapshot in the same scope and continuous access, compute `previousIDs − currentIDs`. For each missing ID, take its login and last-seen time from the previous snapshot and use the new check’s completion time as the upper end of the displayed interval. Same ID with a changed login updates the baseline. IDs returning later rejoin the current list, and a subsequent disappearance can create a new event. Existing count, login, or trend history supplies no starting membership data.
- A different repository ID at the same URL, observed visibility transition, different viewer or credential source, or recovered access after a known denial starts a fresh baseline on the next accepted check and yields no cross-scope disappearance. Persist the continuity break even if the triggering check could not collect a new baseline. Prior events remain local and are visible only within their authorized scope. Fully validate candidate data, current tracked UUID, credential generation, and time order immediately before writing. Reject results from a poll that finishes after untracking or after a newer result has been accepted.
- Atomically replace the validated record with the new baseline and its events together, then publish it to the UI. An absent file is the first-setup case. An unreadable or unknown-version file stays on disk and surfaces a storage error. A failed write preserves the previous record. Untracking clears the repository’s saved stargazer data and invalidates pending results. Mention that deletion in the existing removal confirmation. Keep credentials in Keychain and omit account data from logs, analytics, notifications, and share cards. [Current local persistence](../../../GHMenuStars/Persistence/TrackedRepoStore.swift#L9) · [Confirmed removal flow](../../../GHMenuStars/SettingsView.swift#L306) · [Privacy conventions](../../../README.md#privacy)

## Author details and totals

Use a deterministic profile summary built from public GitHub fields. This draft interprets the author’s total as **Stars received**, the sum of `stargazers_count` across public repositories owned by the stargazer, including public forks. Organization-owned and private repositories are outside that metric. The current repository’s stargazer count appears at the top of the list. [GitHub public user repositories API](https://docs.github.com/en/rest/repos/repos#list-repositories-for-a-user)

1. On account selection, fetch `GET /user/{account_id}` via the existing client. Verify the returned ID and use its current login for profile display and any subsequent login-based API path. Sanitize and truncate user-supplied profile text for display. Omit fields the profile doesn’t supply. Render the bio as plain text. [GitHub user lookup by durable ID](https://docs.github.com/en/rest/users/users#get-a-user-using-their-id)
2. Walk `GET /users/{login}/repos?type=owner&per_page=100`, using strict pagination and checking unique repository IDs, public visibility, and matching `owner.id`. Compare the completed list size to the profile’s `public_repos` when present. An empty repository list requires an explicit public repository count of zero. Sum nonnegative counts using checked integer arithmetic. An access error, concealed profile, repo ownership mismatch, inconsistent count, or interrupted walk shows **Unavailable** for the total while keeping any public profile fields that succeeded. Show when the total was measured because a repository’s star count continues to move.
3. Use the profile’s `blog` and `twitter_username` fields to populate its website and X links. For the selected account only, also read the GitHub social accounts endpoint using its current login and verify that the login still resolves to the same numeric ID before displaying those links. Show LinkedIn and other links the author has supplied through GitHub. Validate URLs, deduplicate links, and open them in the default browser on click. Missing links leave the corresponding space empty. A social accounts error leaves any valid profile links visible. [GitHub profile API](https://docs.github.com/en/rest/users/users#get-a-user-using-their-id) · [GitHub social accounts API](https://docs.github.com/en/rest/users/social-accounts?apiVersion=2022-11-28#list-social-accounts-for-a-user)
4. Automatically load public profile fields for rows in view from a currently authorized snapshot. Load stars received for the selected account and for the rows in view on explicit request. Process the requested authors serially, prioritize the normal repo refresh, and stop queued work when access changes or GitHub asks for cooldown. Deduplicate in-flight work and cache completed public fields, links, and totals in memory by numeric account ID for the running session, with a 24-hour freshness window. A profile failure never changes the repository snapshot or history. Use GitHub profile text, submitted URLs, and numeric sums directly, with no LLM, inferred links, avatar downloads, or profile requests for every account on window open.
